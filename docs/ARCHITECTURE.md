# Architecture

## System map

Four workspaces, one direction of dependency:

```
apps/web ──▶ apps/server ──▶ packages/core ──▶ packages/schemas
   └────────────── shared types ──────────────▶ packages/schemas
```

- **packages/schemas**: Zod schemas, inferred types, fixtures, and the shared API contracts (`view.ts`: `BranchView`, `CreateTimelineRequest`, …). Zero runtime deps beyond zod. Everything an LLM produces is validated against these before it touches any store; the web client parses responses against the same schemas.
- **packages/core**: the pure engine. World store (fork resolution, state replay, and the M18 derivations: claims resolved through visible events, role tenures replayed off the ledger), machine validator, prompt registry, `LLMProvider` port, structured-generation repair loop, `MockProvider`, anchor retrieval, and the curated baseline (assembled out of authored batch files by `scripts/build-baseline.mjs`, which validates before it writes). The pipeline holds the standard era loop plus the two opt-in M17 paths: symposium derivation (`pipeline/symposium.ts`, three specialist drafts and a synthesis) and the Court of Plausibility (inside `pipeline/critic.ts`, advocate and skeptic then a judge). v2/M18 adds `pipeline/claims.ts` (index readings and name drift bound to committed events) and deep-time planning in `pipeline/plan.ts` (`defaultHorizonYears`, spans that keep widening, the optional epilogue span). No IO except through injected ports.
- **apps/server**: Hono on Node. Routes + SSE, `AnthropicProvider`, persistence via Drizzle + better-sqlite3, and the markdown/static-HTML exporters (`src/exporters.ts`). `ANTHROPIC_API_KEY` lives here and only here. Every `/api` route sits behind a 16 MB body limit and an env-driven CORS allowlist (`UCHRONIA_CORS_ORIGINS`); with `UCHRONIA_STATIC_DIR` set it also serves the built web app with SPA fallback (single-container deployment; see `docs/DEPLOY.md`).
- **apps/web**: Vite + React. The RED THREAD interface (binding spec: `docs/DESIGN.md`). react-router in library mode for routing (ADR-0001), TanStack Query for data, TanStack Virtual for the spine, d3 only for thread geometry math, Motion for ink-in, React Aria for dialogs/sliders. The SSE client (`src/lib/sse.ts` + `generation.ts`) folds pipeline frames straight into the query cache so streaming and refetching share one source of truth. Every view is lazily loaded, including `/record` (v2/M16), a read-only browse of the curated baseline reached from Settings.

`StructuredRequest` carries both the rendered prompt (for live models) and the template's structured `args` + a `seedKey` (for the mock); one request shape serves both worlds.

## The structured-output boundary

Every LLM call flows through `generateStructured(provider, template, args)`:
provider completes → JSON parsed → Zod-validated → on failure, re-ask with the validation errors attached (max 2 repairs) → `GenerationValidationError` (fails the batch loudly). Providers never validate; the pipeline owns the boundary.

## Persistence

SQLite (better-sqlite3, WAL) via Drizzle. Tables mirror the schemas one-to-one with JSON columns for nested objects (`apps/server/src/db/schema.ts`); migrations are generated by drizzle-kit into `apps/server/drizzle/` (committed) and applied automatically at `openDatabase()`. No SQL foreign keys: referential integrity is core's job (validator + store guards); deletes run as explicit transactions.

v2/M17 adds the `court_records` table (transcript rows indexed by branch and by event, the ruling stored as JSON) and an `events.contested` boolean column defaulting to false, in migration `0003_past_psynapse.sql`. Court records follow the existing lifecycle paths: aggregate load, aggregate insert (import), timeline delete, and the leaf-branch cascade.

v2/M18 adds the `claims` table in migration `0004_curved_zodiak.sql` (id, branch, event, year, body as JSON, provenance; indexed by branch and by event), and in the same migration widens three existing tables: `convergence_points` gains `attractor` (defaulting to `institutional`), `lateness_years` (defaulting to 0) and a nullable `path_note`; `entities` gains `born_year`, `counterfactual` and `succeeds_slug`; `eras` gains `speculative`. Every added column has a default or is nullable, so the migration is a straight `ALTER` over existing data. Claims travel the same four lifecycle paths as court records. Nothing was added for role tenures: they are derived at view time.

The `Repo` reads whole `TimelineAggregate`s (core's `World` does the thinking) and writes row-granular inserts/updates so the pipeline can persist accepted history as it streams.

## Request flow (reads)

```
GET /api/branches/:id/view
  → repo.branchTimelineId → repo.loadAggregate
  → World.fromAggregate → assembleBranchView (resolve events/eras/edges,
    replay entity state, derive ledgers and role tenures, collect the
    branch's visible court records and claims) → BranchView JSON
```

## Request flow (generation, from M3)

1. Client `POST`s a generation request; server opens an SSE stream.
2. Server hydrates the branch's world from SQLite into core's `World`.
3. Core's pipeline runs (seed → era loop → convergence scan), yielding typed pipeline events. The era step is one `era-generate` call by default, or the symposium's four when the timeline asked for it; the Court of Plausibility sits after the dual review when the timeline asked for that.
4. Server persists each accepted row via `Repo` and forwards the event down the SSE stream (`court.completed` lands in `court_records`, `claim.recorded` in `claims`, like the rest).
5. Client inks events into the timeline as they arrive; aborting the request (Stop button, tab close) cancels in-flight provider calls via AbortSignal and keeps everything accepted so far.

One run per branch at a time (a concurrent request 409s; a unique `(branch_id, ordinal)` index backstops it), a half-persisted trailing era from a crash is healed before the run starts, and token usage is summed against `UCHRONIA_MAX_RUN_TOKENS`.

POD intake (stage 1) already runs synchronously inside `POST /api/timelines`, which is also where the deep-time default lands (v2/M18): a request that names no `horizonYears` gets `defaultHorizonYears(pod.year, thisYear)`, so a divergence runs to the present unless the caller asks for a shorter road.

## Exports

Three formats, all server-rendered: full-timeline JSON (`GET /api/timelines/:id/export.json`, re-importable via `POST /api/import`), branch markdown (`GET /api/branches/:id/export.md`), and a self-contained static HTML edition (`GET /api/branches/:id/export.html`) with the RED THREAD design language inlined, including its typefaces embedded as woff2 data URIs: no scripts, no external requests, readable decades from now. Lifecycle endpoints round the API out: `PATCH /api/timelines/:id` (rename, dial, horizon extension), `POST /api/branches/:b/events/:id/regenerate` (a fresh telling in place), `DELETE /api/branches/:id` (leaf branches only).

## Error taxonomy → HTTP

`ApiError` (route-level) · `NotFoundError` → 404 · `IntegrityError`/`PreForkImmutableError` → 409 · `ZodError` → 400 · `GenerationAbortedError` → 400 · `GenerationValidationError` → 502 · `ProviderAuthError` → 503, other `ProviderError` → 502 · anything else → 500. One envelope everywhere: `{error, message, issues?}`. Mapping lives in `apps/server/src/app.ts`.
